# Лабораторная работа 2. Чтение информации из графических файлов

Формат приложения — WPF (.NET 8), три независимых слоя, как в задании:

```
ImageMetadataViewer.Infrastructure  — Data/Parsing Layer: побайтовые парсеры форматов
ImageMetadataViewer.Engine          — Core/Business Logic: многопоточный обход папки + оркестрация
ImageMetadataViewer.App             — Presentation: таблица, прогресс-бар, предпросмотр картинки
```

`ImageMetadataViewer.Infrastructure` и `ImageMetadataViewer.Engine` не содержат ни одной ссылки на WPF —
это проверяемо по `.csproj` (нет `UseWPF`). Вся логика чтения и обхода
работает независимо от интерфейса.

## Главное архитектурное ограничение — выполнено

**Сторонние библиотеки для метаданных не используются нигде.** Все шесть
форматов (BMP, PNG, GIF, JPEG, TIFF, PCX) разбираются вручную через
`FileStream`/`Stream` по спецификации байт-в-байт — см. `ImageMetadataViewer.Infrastructure/Parsers/`.

Единственное место во всём решении, где используется штатный декодер —
`MainWindow.xaml.cs`, метод показа превью (`BitmapImage`). Это ровно то
исключение, которое разрешено в задании: **рендеринг** картинки в
интерфейсе, а не чтение её свойств. Ширина/высота/глубина цвета и т.д. в
таблице всегда берутся из собственного парсера, а не из `BitmapImage`.

## Как устроено ленивое (потоковое) чтение

Ни один парсер не загружает пиксельные данные целиком:

- **BMP** — читает только 14+40 байт заголовков.
- **PNG** — читает чанк `IHDR` (33 байта от начала), затем идёт по чанкам
  дальше (`длина + Seek`), пока не встретит `IDAT` — до пиксельных данных
  дело не доходит вообще.
- **GIF** — 13 байт Logical Screen Descriptor.
- **PCX** — ровно 128 байт фиксированного заголовка.
- **TIFF** — переходит по смещению на IFD и читает только сами 12-байтные
  записи тегов (плюс, если нужно, по смещению — значение RATIONAL/массива,
  тоже не более нескольких байт).
- **JPEG** — идёт по маркерам сегментов, перепрыгивая ненужные через
  `Seek(длина_сегмента)`, и останавливается сразу после `SOFn` — до
  сжатых данных сканирования (`SOS`) не доходит.

Для проверки повреждённости в конце файла (IEND у PNG, EOI у JPEG,
трейлер у GIF) используется `Seek(..., SeekOrigin.End)` — читаются только
последние несколько байт, а не весь файл.

`Directory.EnumerateFiles` в `FolderScanner` — тоже ленивое перечисление
(это чтение только ИМЁН файлов файловой системой, не их содержимого),
поэтому список из 100000 файлов собирается мгновенно.

## Многопоточность и отзывчивый интерфейс

`FolderScanner.ScanAsync` запускает `Parallel.ForEach` с
`MaxDegreeOfParallelism = Environment.ProcessorCount` внутри `Task.Run`,
так что UI-поток никогда не блокируется. Прогресс возвращается через
`IProgress<ScanProgress>` — стандартный .NET механизм, который сам
переносит вызов колбэка обратно в UI-поток (через `SynchronizationContext`,
захваченный в момент создания `Progress<T>` в UI-потоке), поэтому
`Dispatcher.Invoke` руками нигде не нужен.

Чтобы не заваливать `DataGrid` десятками тысяч мелких обновлений подряд,
результаты сообщаются порциями по 25 файлов (`FolderScanner.BatchSize`),
плюс обязательно в самом конце — таблица заполняется плавно, но без
лишней нагрузки на UI-поток.

Кнопка **«Отмена»** отменяет `CancellationTokenSource`, которым помечен
и `Parallel.ForEach` (через `ParallelOptions.CancellationToken`), и
`Task.Run` — обход останавливается быстро, уже посчитанные результаты
остаются в таблице.

## Детекция повреждённых файлов

Общая защита: `ParserRegistry.ParseFile` оборачивает вызов КАЖДОГО
парсера в `try/catch(Exception)` — то есть даже если в конкретном
парсере есть баг, приложение не упадёт, файл просто получит статус
"Повреждён" с текстом ошибки. Это отдельно от точечных проверок:

- **PNG** — если последние 12 байт файла не образуют чанк `IEND`,
  статус "Повреждён".
- **JPEG** — если последние 2 байта файла не `FF D9`, статус "Повреждён"
  (даже если структура до этого читалась нормально).
- **BMP** — если реальный размер файла меньше `bfSize`, заявленного в
  заголовке, статус "Повреждён" (прямое требование задания: "размер
  файла меньше, чем указано в заголовке").
- **GIF** — если последний байт файла не `0x3B` (трейлер), статус
  "Повреждён".
- **PCX** — если байт Manufacturer не `0x0A`, статус "Повреждён".
- **TIFF** — если смещение на IFD выходит за пределы файла или число
  записей в IFD абсурдно велико, статус "Повреждён".

Все обращения к байтовым массивам идут через `ByteReader.ReadExact` /
`RequireLength`, которые сами бросают понятное `CorruptedFileException`
вместо необработанного `IndexOutOfRangeException` при попытке прочитать
за пределами буфера — файл с подменённым расширением (например,
текстовый файл, переименованный в `.jpg`) закономерно провалит проверку
сигнатуры → попадёт в `ParserRegistry` как "Неизвестно" без падения.

## Что означает каждая колонка таблицы и откуда берётся

| Колонка | Откуда берётся |
|---|---|
| Формат | Определяется по сигнатуре байт (magic number) в начале файла, а НЕ по расширению — расширение может быть подделано |
| Ширина / Высота | Поля width/height конкретного формата (см. комментарии в каждом парсере) |
| DPI X / DPI Y | Разрешение в точках на дюйм. Не у всех форматов есть "родное" понятие DPI: PCX и TIFF хранят его напрямую (TIFF — как RATIONAL + единица измерения), BMP хранит "пикселей на метр" (пересчитывается: ×0.0254), PNG — необязательный чанк `pHYs` (тоже "на метр"), JPEG — необязательный `APP0/JFIF` c явными единицами (дюймы или см). У GIF DPI как понятия в спецификации нет — колонка пустая ("—") |
| Глубина цвета | Суммарное число бит на пиксель. BMP/JPEG/TIFF — берётся прямо из заголовка (умножается на число каналов, где нужно). PNG — `BitDepth × число каналов для ColorType`. GIF — размер палитры в битах (`2^N` цветов → N бит); PCX — `BitsPerPixel × число плоскостей` |
| Сжатие | Для форматов, где оно может отличаться (BMP: RGB/RLE8/RLE4/BITFIELDS; TIFF: Uncompressed/LZW/PackBits/...; PCX: RLE). Для GIF всегда LZW, для PNG всегда Deflate — это фиксировано спецификацией, но всё равно показывается явно, чтобы было видно, что это осознанный, а не пропущенный пункt. Для JPEG показывается тип SOF-маркера (Baseline/Progressive) |
| Доп. инфо | Бонусные необязательные сведения: у GIF — размер палитры в цветах, у PNG — тип цвета (Grayscale/RGB/Индексированный/...) и наличие чересстрочности, у TIFF — порядок байт и число каналов, у PCX — число плоскостей, у BMP — если строки идут "сверху вниз" |
| Статус | OK / Повреждён (наведите курсор на "Повреждён" — во всплывающей подсказке точная причина) |

## Известные упрощения (для честности на защите)

- Для TIFF читается только **первый IFD** (первая "страница") — если в
  файле несколько изображений (multi-page TIFF), возвращаются данные
  только первого.
- Для JPEG чтение останавливается на первом `SOFn` — если в файле
  несколько кадров (что практически не встречается в обычных JPEG),
  учитывается только первый.
- `FolderScanner` сканирует только **указанную папку** без вложенных
  подпапок (`SearchOption.TopDirectoryOnly`) — под условие задачи ("папка,
  содержащая до 100000 файлов") это осознанно достаточно.

## Как собрать и запустить

Через Visual Studio 2022+: открыть `ImageMetadataViewer.sln`, **правой кнопкой по
ImageMetadataViewer.App → Set as Startup Project**, затем F5.

Через консоль:
```
dotnet build
dotnet run --project ImageMetadataViewer.App
```

## Структура файлов

```
ImageMetadataViewer.sln
ImageMetadataViewer.Infrastructure/
  ImageMetadata.cs        — DTO с результатом чтения одного файла
  IImageParser.cs          — контракт парсера
  ByteReader.cs             — безопасное чтение чисел из байт (LE/BE) + CorruptedFileException
  ParserRegistry.cs          — выбор парсера по сигнатуре, гарантия "не упасть"
  Parsers/
    BmpParser.cs, PngParser.cs, GifParser.cs,
    JpegParser.cs, TiffParser.cs, PcxParser.cs
ImageMetadataViewer.Engine/
  ScanProgress.cs           — DTO для отчёта о прогрессе
  FolderScanner.cs           — Parallel.ForEach по папке, батчинг прогресса, отмена
ImageMetadataViewer.App/
  MainWindow.xaml(.cs)       — View: таблица, прогресс-бар, предпросмотр
  MainWindowViewModel.cs      — Controller: состояние сканирования
  Converters.cs                — форматирование ячеек таблицы (null → "—", статус, цвет)
```
